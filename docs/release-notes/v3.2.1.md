# v3.2.1 — patch: surface upstream rate-limit hints (root cause of empty responses)

> 2026-08-03 · 2 commits since v3.2.0 · fixes the intermittent empty-response issue

## The bug

When requests exceed the upstream frequency threshold, `chat.deepseek.com`
returns **HTTP 200 with an SSE `event: hint` frame** and **no content
tokens**:

```
event: hint
data: {"type":"error","content":"消息发送过于频繁，请稍后重试","clear_response":true,"finish_reason":"rate_limit_reached"}
```

(The Chinese `content` above is the literal upstream text — "messages sent too
frequently, please retry later".)

The adapter only parsed `toast` events, not `hint` — so a rate-limited
request was silently turned into `200 OK` with empty `content` / an empty
stream. That looked like an intermittent "empty response" bug (and made the
web-side history show unanswered or successful-looking requests).

## The fix

- `adapter.py` — new `UpstreamHintError` and `RateLimitError`; the
  non-streaming path scans parsed events with `_scan_hint_errors()`, the
  streaming path detects the `hint` frame inline (mirroring the existing
  `toast` handling)
- `server.py` — `RateLimitError` maps to **HTTP 429** ("Upstream rate limited:
  messages sent too frequently, please retry later"); other hint errors map to
  502 with the upstream message

A rate-limited request now returns an explicit `429` the client can back
off from, instead of a fake-successful empty completion.

## Guidance

- Space out requests (`DEEPSEEK_JITTER_SECS=0.4`) or spread load across
  multiple accounts in the pool
- If an empty response still occurs without the 429 after this patch,
  please open an issue with the raw SSE slice — that would be a genuinely
  different case

## Verified

- Unit: rate-limit SSE → `RateLimitError`; non-rate hint → `UpstreamHintError`; normal SSE untouched
- 56 pytest unit tests green
